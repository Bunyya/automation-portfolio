# Архитектура

Модуль отделяет принятие решения от выполнения действия. `InputMessage` проверяет поля входящего сообщения; `classify()` распознаёт явный префикс; `plan()` подготавливает текст и список синтетических получателей; `NotificationService` координирует попытки и состояние; `SimulatedSink` собирает результат в памяти.

## Поток обработки

1. CLI читает JSON-массив и проверяет `message_id`, `text`, `audience`.
2. Классификатор возвращает категорию `announcement`, `reminder`, `urgent` или `unrecognized`.
3. Планировщик выбирает `demo-students` либо `demo-staff`. Для `urgent` добавляет `demo-operators`.
4. Симулятор сохраняет подготовленные уведомления в памяти. Параметр `--fail-recipient` создаёт контролируемую ошибку одного получателя.
5. SQLite записывает статус отдельно для каждой пары `(message_id, recipient)`.

## Повторы и ошибки

`message_registry` содержит ID сообщения, SHA-256 от текста и аудитории, категорию. `delivery_attempts` содержит получателя, статус, число попыток и фиксированный код ошибки. Успешное действие пропускается при повторной обработке, неудачное можно повторить. Если тот же ID пришёл с изменённым текстом или аудиторией, операция отклоняется.

В тестовом адаптере нет сетевых вызовов. Ожидаемая ошибка симулятора фиксируется как неудачная попытка; неожиданная ошибка программы прерывает обработку и откатывает транзакцию SQLite. Вывод симулятора хранится в памяти и не является транзакционной частью базы. Поэтому даже в этой модели нельзя трактовать запись статуса как универсальную гарантию доставки «ровно один раз». При подключении внешнего API понадобятся отдельная модель доставки и правила повторов.

## Границы

- Правила классификации заданы явно; обучение модели и генерация текста отсутствуют.
- Вывод адресуется только вымышленным получателям и не покидает процесс.
- База не хранит исходный текст, но содержит ID и хеш; для запуска следует использовать синтетические сообщения.
